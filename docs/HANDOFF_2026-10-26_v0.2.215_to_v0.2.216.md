## D. Next feature: v0.2.216 historical/batch property registration

### Why it is needed

The owner supplied screenshots of a legacy Inventory Management “Add Inventory / Edit Inventory” flow and wants the *behavior* modernized within IPDAMS's existing Property Accountability UI. Users must register equipment and property acquired **before IPDAMS**, even when the items have no system-created PO, IAR or DV. Avoid a separate, duplicate asset ledger.

### Required functionality

- **Historical registration** with optional typed evidence references: PO No., IAR No. and DV No. These are **historical references only**; they must **not** create official PO/IAR/DV documents, automatically link by ambiguous number, change the fund ledger or initiate stock/accounting postings.
- **Register from finalized/accepted IAR** using verified **existing system** document links and remaining eligible quantities; preserve accepted-IAR, custody, stock and duplicate-registration controls.
- **Batch-common details** captured once for identical units: classification/description, brand, model, acquisition method/date, cost, useful life, optional historical source references and notes.
- **Per-unit details**: unique automatically assigned property number, serial number, physical location, condition, legacy tag and historical custodian reference.
- **Automatic tag numbering** continues v0.2.213 rule. Example: `306351-2610-00001` followed in a new month by `306351-2611-00002`, **never reset when YYMM changes**. Each school has an independent lifetime counter. Property numbers are immutable once assigned; concurrency and transaction rollback matter.
- **Edit Property** supports either the *exact common registration batch* or *one unit*, but protects issued/finalized ICS/PAR accountability and never silently changes a custodian, school, number, value, source IAR or issued document. Preserve append-only before/after audit and stale-edit rejection; changes to actual accountability must use proper movement/ICS/PAR workflow.
- Current implementation stores the new batch relationship/profile on existing `assets` records through proposed **additive** columns `registration_batch_key VARCHAR(48) NULL` and `property_profile TEXT NULL`; no second asset ledger or transaction posting by installation.
- One discovered and fixed defect: saved shared property `origin` returned in edit preview must be accepted **only if identical to the server-verified source** (`HISTORICAL_OPENING` / `VERIFIED_IAR`), never changed by client input.

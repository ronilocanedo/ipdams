# v0.2.264 — Receiving Property Custodian Condition Assessment

**Recorded installed predecessor:** v0.2.263 (owner confirmed 2026-11-02).
**Status:** GitHub integration in progress, not deployed and not yet packaged as an approved updater.

## Root cause confirmed in installed Hostinger source
The receiving office's `api/property-transfer-intake.php` has a Received Asset Register and Property History but no post-acceptance **Assess condition** action. The existing `app/Domain.php` deliberately blocks ICS/PAR issuance of a received transfer unless its current property condition is `Serviceable`. This rule must not be weakened.

## Required change
1. Allow only the currently appointed and bound, active receiving Property Custodian of the receiving SCHOOL or DIVISION organization to assess its own transferred-in asset.
2. Show an **Assess condition** link for active transferred-in properties in Received Asset Register; require date, observed condition, signed inspection/repair reference, findings/reason, and affirmative physical-inspection attestation.
3. On the backend, validate the current appointment and login binding, scoped receiving organization, authenticated receipt lineage, unassigned asset, no active ICS/PAR, and no conflicting formal disposal/unserviceability lifecycle decision.
4. Use a database transaction with tenant and asset row locks, revalidate current user, old condition and date, and change only `assets.condition_note`. Append an `audit_events` entry recording previous/new condition, inspector, evidence reference and reason.
5. Leave original transfer document, source-school history, original receiving inspection, physical custody, issued ICS/PAR, document numbers, procurement, asset value, fund, bank, stock and journal untouched.
6. Preserve separate `accountability.issue` checks and mandatory formal Property Condition & Disposal workflow.
